▸SECS Compatibility Tier

Three tiers describe how a product relates to the SECS governance substrate. Tier is determined by evidence, not intent.

SECS Adjacent Operates in a related functional space. Shares terminology or intent with one or more SECS governance layers but is architecturally independent.

SECS Compatible Architecturally capable of adaptor integration. Could interface with the SECS substrate as a certified external process without structural conflict.

SECS Compliant * Has undergone proprietary SECS compliance assessment. No product currently holds this classification.

* SECS Compliant — Compliance Alpha

SECS Compliant classification requires proprietary assessment using SECS interface tooling. This includes automated drift analysis, critical field mapping, guardrail conformance testing, and deep codebase audit through certified adaptor development and deployment toolchains. No product currently holds this classification. Assessment is available under NDA.

▸Architecture Type

Six architecture types describe where a product sits relative to the execution path. Type is determined by what the product can structurally do, not what it claims to do.

Hot-Path Sits on the execution path. Can refuse, halt, transform.

Sidecar Observes or audits alongside execution. Cannot halt.

Bolt-On Added after build. Retrofitted governance. Not architectural.

Wrapper Wraps an existing system. Intercepts at API boundary only.

Policy Layer Defines rules. Does not enforce them at runtime.

Description Describes governance. Framework, taxonomy, or position paper.

▸How Products Are Classified

Every product follows the same assessment workflow. No exceptions. No favours.

StepWhat Happens
1. CapturePublic-facing content is captured: headline, about, featured, pinned, recent activity.
2. ExtractEvery architectural and technical claim is listed verbatim with its source location.
3. EvidenceEach claim is classified: Demonstrated (code, spec, artefact), Described intent (narrative), Meta-claim (about the project), Tagline, or Personal context.
4. FlagClaims marked: ✅ Clear, ⚠ Ambiguous, or 🔴 Unsupported.
5. ClassifySECS Tier + Architecture Type + Functional Layer mapping assigned based on evidence.
6. PublishAssessment file created. Table updated. Tracker synced.

Evidence Types

DemonstratedPublic code, protocol spec, API, runtime artefact, test results, or formal model.
Described intentStated in natural language — what it aims to do. No artefact.
Meta-claimStatement about the project itself — versioning, protection, scope. Not technical.
TaglineMarketing or branding language. Principle or slogan. Not testable.
Personal contextBiographical. Informs motivation, not architecture.
